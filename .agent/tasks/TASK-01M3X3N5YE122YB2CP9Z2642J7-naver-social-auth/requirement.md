# Requirement

## Background / Goal

구글·카카오 소셜 로그인에 네이버를 추가한다. 자체 비밀번호 회원가입은 없다.
사용자는 2026-10-02 공식 계약 확인과 방식 제안 후 서버 코드 교환 구현 및 모바일 참고 docs 작성을 승인했다.
기준 브랜치: feat/auth. 카카오 구현 커밋: 8e0af89.
네이버 프로필에는 발급 대상 앱을 확인할 필드가 문서화되어 있지 않으므로 서버의 우리 앱 Client ID·Secret으로 인가 코드를 교환한다.
인증 입력은 기존 credential(네이버에서는 code)과 네이버 전용 state다. 클라이언트는 원래 로그인 시도와 state를 검증한 후 API를 호출한다.
서버는 state의 형식만 검사하고 교환 요청에 전달한다. 서버의 state 보관·대조와 로그인 시작 API는 이번 범위에 없다.

## R1 - 네이버 서버 인증

- AC-R1-1: 네이버가 검증한 사용자 식별자로 회원을 연결한다. 클라이언트가 보낸 subject나 이메일만으로 인증하지 않는다.
- AC-R1-2: 선택한 인증 방식으로 우리 앱에 발급된 인증 정보임을 확인한다. 단순 프로필 조회가 앱 귀속까지 증명한다고 가정하지 않는다.
- AC-R1-3: 잘못된·만료된 인증 정보와 외부 서버 장애·통신 실패·타임아웃을 구분한다. 실패 시 회원과 세션을 처리하지 않는다.

## R2 - 설정과 의존성 연결

- AC-R2-1: 공식 계약에 필요한 설정을 확인하고 누락·잘못된 설정을 모듈 구성 시 검증한다. 비밀 정보는 저장소에 남기지 않는다.
- AC-R2-2: SocialAuthProvider 구현을 AuthModule에 등록하고 검증된 (naver, subject)를 기존 회원 연결 흐름에 전달한다. 구글·카카오 동작을 유지한다.

필수 환경 변수는 NAVER_CLIENT_ID·NAVER_CLIENT_SECRET이다. Callback URL은 모바일·제공자 콘솔에서 관리한다.

## R3 - 기존 HTTP 로그인 확장

- AC-R3-1: POST /auth/social/login에서 naver를 지원하고 검증된 신규·기존 회원에게 기존 형식의 서비스 토큰과 세션을 발급한다.
- AC-R3-2: 입력 오류·인증 실패·외부 장애는 공통 오류 계약을 따르며 원문 credential과 외부 내부 내용을 노출하지 않는다.

네이버 HTTP 본문은 `{ provider: "naver", credential: "인가 코드", state: "클라이언트가 검증한 state" }`다.
구글·카카오는 기존 두 필드 형식을 유지하고 state를 허용하지 않는다. 네이버 토큰은 DB·서비스 응답에 남기지 않는다.

## R4 - 모바일 참고 문서

- AC-R4-1: docs/social-login-process.md에 제공자별 단계·서버 입력·앱 귀속 확인·서비스 토큰 처리를 정리한다.
- AC-R4-2: state/nonce의 목적과 모바일·서버 책임, 현재 미구현 모바일 영역 및 실제 제공자 검증의 한계를 명시한다.

## Out of Scope

모바일 로그인 화면·SDK, 프로필 수집, 이메일 기반 자동 계정 통합, 네이버 토큰 갱신·연결 해제, DB 스키마 변경, auth PR/push/병합.
서버 로그인 시작 API·state 저장소, 구글 nonce 검증 API 확장, 모바일 SDK 선택·구현은 제외한다.
